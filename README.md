# mutex(ミューテックス)

**複数のスレッドが共有データに同時にアクセスするのを防ぐ為の同期メカニズム**

## 排他制御とは

マルチスレッドプログラミングにおける排他制御とは「**複数のスレッド間で共有するデータへの同時アクセスによってデータの不整合が起こる場合に、その共有するデータへ同時にアクセスできるスレッド数を制限する**」こと

mutexによる排他制御

mutexとは、**クリティカルセクションを1つのスレッドしか進行できない「鍵付きの個室」として扱うことで排他制御を実現する仕組み**

# デッドロック / リソーススタベーション

# デッドロック

## **状態**

**２つ以上の複数のスレッド / プロセスが互いにリソースの解放を待機して、全員が永久に進めなくなっている状態**

## **デットロックが起きる条件**

1. **相互排他**
    1. あるリソースは同時に１つのスレッド / プロセスしか使えない
    2. 例、フォーク１本は同時に２人で持てない
2. **保持して待つ**
    1. すでにどこかのリソースを持ったまま、追加のリソースを待つ
    2. 例、左フォークは握っている状態で、右フォークを待ち続ける
3. **非奪取**
    1. リソースは「自分から手放す」以外に、他人から強制的に奪えない
    2. 例、右フォークが欲しいからといって、右隣から取り上げることができない
4. **循環待ち**
    1. **A**が**B**のリソースを待ち、**B**が**C**のリソースを待ち…最後に**Z**が**A**のリソースを待つという**輪っか状の待ち**ができている
    2. 例、**Philo_A**は**Philo_B**のフォーク待ち、**Philo_B**は**Philo_C**のフォーク待ち…**Philo_Z**は**Philo_A**のフォーク待ち

この4つのうちどれか1つを壊すことで理論上デッドロックは防げる

## **例：**

- 各哲学者 = 1スレッド
- 各フォーク = 1本ずつ mutex で守られたリソース
- 全員が「まず左のフォークを取る」と決めているとする。
1. みんな同時に左フォークを `pthread_mutex_lock` で取る。
2. 右フォークを取ろうとするが、右隣の人が既に左として持っている。
3. みんな「右フォーク待ち」で `pthread_mutex_lock` の中で止まりっぱなし。
4. 誰もフォークを離さないので、**全員が永久に待ち続ける → デッドロック**。

# リソーススタベーション

## **状態**

**スレッド / プロセスが、他の処理（スレッド / プロセス）にリソースを取られ続けてなかなか / 永久に実行の機会を得られない状態**

システム全体としては進んでいる

でも特定の誰かだけがずっと「待ち続け」になる

## 例：

- スケジューラ（あるいは自分の fairness ロジック）が「IDの小さい哲学者を優先」としている。
- ID の大きい哲学者がフォークを取ろうとすると、
    
    そのたびに ID の小さい哲学者が先にフォークを取ってしまう。
    
- シミュレーション時間が有限なら「ほぼ食べられない」、理論上は「永久に食べられない」こともありうる。
    
    → **この哲学者だけが starvation**。
    

**原因**

スケジューリングアルゴリズムが特定のプロセスを優先し続ける、またはリソースのリーク

# デッドロックとリソーススタベーションの違い

## デッドロック

全体の進行：**止まる**

特定のスレッド：**全員止まる**

典型例：**全員がフォークを1本ずつ掴んで待つ**

## リソーススタベーション

全体の進行：**動く**

特定スレッド：**一部だけ止まる**

典型例：**優先度の低いスレッドがいつも後回し**


# スレッドとプロセスの違い

| **名称** | **概要** | **利用するメモリ空間** | **終了の仕方** | **終了の際の注意** |
| --- | --- | --- | --- | --- |
| **プロセス** | 実行されたプログラム | 自身のメモリ空間 | 実行者が終了 or プログラム処理の終了 | - |
| **スレッド** | プロセス内で作成された、独立して動作することの出来る関数 | 親プロセスのメモリ空間 | プロセスによる終了 or 自身で終了 | プロセスと連携して正しく終了しないとメモリリークします |
| **子プロセス** | プロセス内で実行された、別プログラム | 自身のメモリ空間 | プロセスによる終了 or 自身で終了 | プロセスと連携して正しく終了しないと子プロセスの残骸(ゾンビプロセスと呼ばれる)が残ります |

## プロセスが持っているリソース

- **コードセグメント**
    
    → 実行する命令そのもの（バイナリの機械語）
    
- **データセグメント**
    
    → グローバル変数や `static` 変数
    
- **ヒープ**
    
    → `malloc` / `new` で確保される動的メモリ
    
- **スタック**
    
    → 関数呼び出し、ローカル変数、引数など
    
- **レジスタ**
    
    → CPU内部の超高速な小さなメモリ（計算途中の値や次の命令位置など）

# スレッド

**「プロセス内の実行単位」**

**1つのプロセスの中で動く「処理の流れ」**

- **シングルスレッド**：スレッドが1本しかないプロセス
- **マルチスレッド**：スレッドが複数あるプロセス

**スレッドごとに別なのは**

- レジスタ
- スタック

**スレッド同士で共有しているのは**

- コードセグメント（命令）
- データセグメント（グローバル変数など）
- ヒープ

同じプロセス内のスレッドたちは、

**同じメモリ空間を共有しつつ、各自のスタックを持って動いている**

### メリット・デメリット

- **メリット**
    - プロセスの中でメモリ共有しているので、
        
        スレッド同士のデータのやり取りが **高速で効率的**
        
    - スレッド間の切り替えは、プロセス同士の切り替えより **軽い**
- **デメリット**
    - 1本のスレッドのバグで、**プロセス全体のメモリを壊す**可能性がある
    - だから、ミューテックスなどで **正しく同期** をとらないといけない

# プロセス

**「実行中のプログラムのから実際に作られたモノ」= OSが管理するプログラムの実行単位**

### プロセスのメモリ空間

- **各プロセスは「独立したメモリアドレス空間」を持つ**
    
    →別のプロセスから直接そのメモリは触れない（壁があるイメージ）
    
- 他のプロセスのメモリを壊されにくくて安全
- でも、プロセス同士を切り替えるときは、
    
    OSがいろいろ入れ替えるのでオーバーヘッド（余計な処理コスト）が大きい
    

### 例：

- Chrome では **タブごとにプロセス** を分けている。
- あるタブがクラッシュしても、他のタブに影響しにくい。
- タブごとにメモリ管理や負荷制御ができる。

→ **「1タブ = ほぼ1プロセス」** というイメージ。

## プロセスとスレッドの違い

| 観点 | プロセス | スレッド |
| --- | --- | --- |
| 実行単位 | 「実行中のプログラム本体」 | 「プロセス内の実行の流れ」 |
| リソース管理単位 | **コード / データ / ヒープ / スタック / レジスタ** | **レジスタ・スタックだけ別、他はプロセス内で共有** |
| メモリアドレス空間 | プロセスごとに完全に独立 | 同じプロセス内のスレッドで **アドレス空間を共有** |
| 並行処理 | プロセス間で並行 → **IPC** が必要 | 同一プロセス内のマルチスレッドで並行処理 |
| 切り替えコスト | 重い（オーバーヘッド大） | 軽い |
| 安全性 | 他プロセスのメモリを直接壊せない（安全寄り） | 1スレッドのミスでプロセス全体のメモリを壊しうる |

**IPC（Inter-Process Communication）**

プロセス同士がデータをやり取りする仕組み。

例：パイプ、ソケット、共有メモリ、メッセージキュー など。

- **コードセグメント**
    
    → 実行する命令そのもの（バイナリの機械語）
    
- **データセグメント**
    
    → グローバル変数や `static` 変数
    
- **ヒープ**
    
    → `malloc` / `new` で確保される動的メモリ
    
- **スタック**
    
    → 関数呼び出し、ローカル変数、引数など
    
- **レジスタ**
    
    → CPU内部の超高速な小さなメモリ（計算途中の値や次の命令位置など）


# マルチスレッドの概要

### イメージとして

仕事（スレッド）をするのがCPUのコア。

スレッドを仕事として例えるのであれば、コアは仕事をする人

つまり、マルチスレッドは同時に複数の仕事をこなすことが可能

具体的には、マルチスレッドというのは、**仕事（スレッド）を複数の仕事に分割した細分化された仕事**

## 並行性と並列性

---

- **並行性（concurrency）**
    - シングルコアCPUでマルチスレッドを動かすときの状態。
    - CPUは１回に１つのスレッドしか実行できないけど
        - とても高速に
        
        「スレッドA →スレッドB →スレッドC →…」
        
        と切り替えて動かすので
        
    - 人間から見ると「同時に動いているように見える」状態。
    - 実際には **同時ではなく”順番にちょっとずつ”** 動いているだけ。

- **並列性（parallelism）**
    - **マルチコアCPU（マルチプロセッサ）**でマルチスレッドを動かすときの状態。
    - スレッドAはコア０、スレッドBはコア１…のように、　**物理的に同時**に動いている。
    - 例えば４コアがあれば、４スレッドを本当に「同時実行」できる。

# データ競合・競合状態

## データ競合とは

**複数スレッド間で共有する変数に対して、同時に、読み / 書きアクセスが行われること**

より厳密に言えば

「少なくとも1つが書き出し（write）操作である複数のアクセス」となる

つまり、**全スレッドが読込（read）操作**なら、データ競合は生じない

また、 `++i` や `i *= 2;` のような値の更新処理は、読込 - 更新 - 書出（RMW: Read - Modify - Write）操作と呼ばれ、文字通り書出（write）操作の一種として扱う

- **同じメモリ上の場所**（同じ変数など）に
- **2つ以上のスレッド**からアクセスがあり
- そのうち**少なくとも1つは書き込み（write）**で
- そのアクセス同士が**適切な同期（mutex, atomic など）で順序付けされていない**

**同期（synchronization）**

- スレッド同士の「順番」や「同時に触っちゃダメな場所」を調整する仕組み
- 例：`pthread_mutex_t`（mutex）、`pthread_cond_t`（条件変数）、`atomic` 変数、`join` など

## 競合状態とは

**イベントやスレッドの実行順序・タイミングによって結果が変わってしまう**

**設計・ロジック上の問題**

- 「同じ変数に同時アクセス」とは限らない
- OS の処理順序・I/O のタイミング・ロックの取り方など
    
    **いろんな“順番”に依存してバグが出る状態**全般を指すこと
    

競合状態の例

ファイルの存在チェックと作成を別々に行うコード：

1. プロセス A：`if (ファイルが存在しない)` をチェック
2. プロセス B：その間に同じ名前のファイルを作成
3. プロセス A：`新規作成` だと思って処理を続行 → 思っていないファイルを上書き など…

## データ競合と競合状態の関係
|  | データ競合（data race / データ競合） | 競合状態（race condition / 競合状態） |
| --- | --- | --- |
| 範囲 | **メモリアクセスに特化した狭い概念** | **実行順序・タイミングが絡むバグ全般の広い概念** |
| 条件 | 同じメモリ、複数スレッド、同期なし、少なくとも1つは書き込み | 実行順序によって結果が変わる・バグになる |
| 例 | `counter++` をロックなしで複数スレッドから実行 | ファイル存在チェック後に他プロセスが書き換える など |
| 検出のしやすさ | 機械的に判定しやすいのでツール向き | 多くは設計・ロジックの問題で、ツールだけでは難しい |
| 関係 | **race condition の一種** | data race を含むより広い概念 |


# 実行時の便利ツール

### 通常 `valgrind` コマンド

```bash
valgrind --leak-check=full -s -q ./philo
```

### 子プロセスまで確認する `valgrind` コマンド

```bash
valgrind --trace-children=yes -q ./philo
```

### `-trace-children=yes`

ここがポイントのオプションです。

- 意味：
    
    **`./philo` が `fork` や `execve` などで「子プロセス」を起動したとき、その子プロセスも Valgrind の監視対象にする**。
    
- デフォルト（何も指定しない場合）
    - `-trace-children=no` 相当で、
    
    **「親プロセスだけ」**が Valgrind の対象です。
    
    `execve` などで別プログラムを起動しても、その子は Valgrind なしで動きます。
    
- `yes` にするとどうなるか
    - 親が `execve("ls", ...)` で `ls` を起動 ⇒ その `ls` も Valgrind の下で実行される
    - Webサーバーやシェル、テストランナーなど、**子プロセスをバンバン起動するタイプのプログラム**のときに、
        
        「親だけじゃなく、実際に動くコマンド側のリークも見たい」というときに使う
        

### **データ競合を確認する `valgrind`コマンド**

```bash
valgrind --tool=helgrind -q ./philo
```

### `-tool=helgrind`

- Valgrind の **Helgrind ツールを使う**指定。
- 主な用途：
    - `pthread_mutex` のロック・アンロックの使い方が正しいか
    - **データ競合 (data race)** が起きていないか
        
        （複数スレッドが同じ変数を、ロック無しで同時に読み書きしてないか）
        

Philosophers のようなマルチスレッド課題との相性が良く、

- `last_meal_ms` や `meals_eaten` をロック無しで読んでいないか
- `stop` フラグをロック無しで読んでいないか

などを検査できます。

### デッドロックを確認する `valgrind` コマンド

```bash
valgrind --tool=drd -q ./philo
```

### `-tool=drd`

- Valgrind の **DRD (Data Race Detector)** ツールを使う指定。
- 役割は Helgrind とかなり似ていて、こちらも
    - データ競合
    - ロックの順序問題（デッドロックの原因になるもの）

などを検出します。

実運用では、

- `helgrind` で警告を見る
- `drd` でも試してみて、別の観点の警告が出ないか確認

みたいに**「別の検査エンジン」**として両方を使い分ける感じです。

ただし **同時に 2 つは使えない**ので、普通はどちらか一方だけ指定します。

### 食事の回数を見る

結果を `test.txt` などに入れる

```bash
./philo 5 800 200 200 7 >test.txt 
```

この例の場合７回食事をしなくてはいけないのでそれをあぶり出す

```bash
grep "[ID] is eating" -R
```

これで回数を見れる

```bash
grep "[ID] is eating" -R | wc -l
```

Makefileにコンパイラオプションとしてこれを付ける

**スレッドまわりのバグ（データ競合や一部の同期ミス）を実行時に検出するためのオプション**

```bash
-fsanitize=thread
```
